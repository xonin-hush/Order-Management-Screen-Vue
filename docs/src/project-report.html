How it works

Architecture

  • Server state lives in TanStack Vue Query, one cache entry per search, so a slow older response can never replace newer results.
  • The session (token, user, permissions) is the only Pinia store.
  • Every request goes through one axios instance whose interceptors attach the token and turn failures into one typed ApiError.
  • Forms run on TanStack Form and validate with the zod schema the mock uses, so 422 errors land under the matching fields.
  • The UI is Vuetify 4. Its theme and component defaults define every shared style once.
  • Loaders sit on what's loading: skeletons shaped like the screen they replace, a bar on the results while a search or filter updates them.
  • Filters and the open panel live in the URL, so refresh, Back and shared links work.

Permission model

  • The UI checks permissions, never roles: session.can('orders.cancel'). Roles exist only on the server.
  • No permission → hidden. Allowed, but blocked by the order's state → disabled, with the reason on screen.
  • The mock enforces every rule again: 401 ends the session, 403 is explained and /me re-read, 409 for final orders, 422 per field.
  • One rule beyond the brief: creating or editing also needs orders.view_amount, since orders carry prices.

Beyond the automated tests

  • Every flow was also exercised in real Chrome with Playwright scripts, at 1280 px and 375 px, for each role.
  • Two review rounds with parallel reviewers (requirements, correctness, security, accessibility and UX, code quality), each finding checked by an adversarial verifier. Confirmed issues were fixed, with a regression test where the fix could be tested.
  • A UI pass went through every loading, empty and error state in Chrome at 1280, 900 and 375 px, against the dev server and the production build. What it found was fixed, again with a regression test where the fix could be tested.
