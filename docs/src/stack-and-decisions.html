Decisions that shape the code

01Permissions, never roles

Code asks session.can('orders.cancel'). Roles exist only on the server, so a new role needs no client change. With no permission, an action is hidden: it never applies to this user. Allowed but blocked by the order’s state, it is disabled with the reason on screen.

02The server has the final say

The mock re-checks every rule in a fixed order: 401 → 403 → 404 → 409 → 422. Responses are built field by field from an allow-list, so a new field never reaches Support by accident. A 403 is about the user, so /me is re-read; a 409 is about the order, so the order is refetched.

03A session ends one way

Sign-out and a 401 share endSession(): forget the token, go to sign-in, clear the query cache and pending saves, reset the store, revoke the token. Responses sent with an old token are discarded, so nothing reaches the next user. A 403 never signs anyone out.

04The URL is the state

Filters and the open panel live in the URL (/orders/12?status=pending), so refresh, Back and shared links work. Search waits for a 300 ms pause, and the list always matches the search box.

05One form, one schema

Create and edit share one form and the zod schema the mock validates with. 422 errors appear under their fields and stay with their line item when another is removed. Edit works on a copy, so a background refresh never overwrites typing.

06Failure is part of the demo

The Mock API panel makes the next order request fail with a 500, network error, 401, 403 or 422, then switches itself off, so a reviewer sees the error and then the recovery. It works over an open order panel too. Loads retry once, saves never.

07Loaders sit on what's loading

Skeletons have the shape of the table, list, panel and form they stand in for, so nothing moves when data arrives. A search or filter puts a bar on the results, not in the search box; a page still downloading puts one under the app bar.

08One look in dev and production

Vuetify ranks its CSS in cascade layers, ordered by first appearance, and the build links component CSS before the file that declares them. index.html declares the order first; without it, built buttons drew 16 px text where dev showed 14 px.

Trade-offs I accepted

Token in localStorage The mock runs in the browser. In production the token becomes an httpOnly cookie, a change confined to http.ts and the auth feature.
409, not 403, for final orders Changing a delivered or cancelled order fails even for Admin. The block comes from the order’s state, not the user’s rights.
One rule beyond the brief Creating or editing also needs orders.view_amount: orders carry prices, and a role that can’t see them shouldn’t overwrite them.
No pagination Fifty orders fit in one response. Server-side pagination and sorting are the first next step.
~34 KB gzipped for phone numbers libphonenumber-js loads only with the order panels. Iraq-only metadata would cut it to a few KB.

Deliberately not added: a date library (Intl formats IQD and dates), an i18n library, stores for UI state (the URL holds it), and CI with Playwright end-to-end tests, which the README lists as next steps.
